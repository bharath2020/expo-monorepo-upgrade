# Role: report

tier: cheap

- **Inputs:** `reports/<run-id>/state.json`, `events.jsonl`, `journal.md`, every cluster findings file, `target_sdk`, and the learnings home, `docs/upgrades/`.
- **Loads:** `references/worker-briefs.md`, `references/schemas/report.md`, `references/schemas/ledger.md`.
- **Contract:**
  1. Read only the whole ledger — `state.json`, `events.jsonl`, and `journal.md`, the three files `references/schemas/ledger.md` defines it as — plus the cluster findings, never orchestrator memory or raw logs. `journal.md` carries the run's narrative reasoning, so a finding that lives only there still reaches the learnings doc.
  2. Fill every field in `references/schemas/report.md`: `overview`, `clusters[]`, `decisions[]`, `timeline[]`, `follow_ups[]`. Set each lane's `overview.lane_outcomes` from its final matrix state, `blocked` where a cluster closed the lane short, and give every blocked cluster its `recommended_next_step`. Add a `suggested_action` follow-up wherever a standing `expo-upgrade.yaml` entry — a gate correction, a missing capability — would have served this run better, naming the `expo-monorepo-upgrade-setup` skill as the way to record it (A10, A11).
  3. Set `pre_existing: true` for any cluster whose gate/app/platform cell was already red in `state.json.baseline`. Baseline runs no T3 gate, so where the run holds any T3 cluster, add a `warning` follow-up naming the suite and saying it was never baselined — those clusters are unproven either way, not proven new.
  4. Flag the structural changes first: every cluster whose findings record a hoisting-ladder rung (`references/monorepo-hoisting.md`) or an edit to shared/root config earns a `follow_ups[]` entry of type `warning`, ahead of every other follow-up — these change the whole workspace, not one app.
  5. Derive `summary.md` as free prose from `report.json` — no separate schema, no styling opinions. Write both to `reports/<run-id>/`.
  6. Write or append `<learnings home>/sdk-<target>.md`: clusters that hit this repo, root causes, fixes that worked, repo gotchas, decisions and rationale, opening with step 4's structural changes. Append your run's entry below whatever the file already holds — a prior run's entry and a human's note both survive verbatim.
  7. Render `report.html` once every artifact above is on disk with the skill's bundled renderer, `node <skill-dir>/scripts/render-report.mjs <run-id>` from the repo root — it reads `report.json`, `state.json`, and `events.jsonl` and needs no dependencies. Then open it for the human — `open <path>` on darwin, `xdg-open <path>` elsewhere. A renderer or an open that fails becomes a `follow_ups[]` warning naming it, rewritten into `report.json` and `summary.md` before the commit below; the report itself still stands.
  8. Commit the learnings doc and the report artifacts on `upgrade/sdk-<target>` as `docs(sdk-<target>): upgrade learnings and run report`. Where the repo gitignores `reports/`, commit the learnings doc alone and say so in the verdict — a repo that ignores run artifacts keeps ignoring them. Test that with `git check-ignore reports/`, trailing slash included: a directory-only `.gitignore` pattern (`reports/`) never matches a path git cannot see is a directory, so the bare name answers "not ignored" on a directory that does not exist yet.
- **Verdict:** `references/schemas/verdict.md`'s non-gate shape — `status` `green` when every artifact above landed and `blocked` when one could not be written, the three coverage fields `null`, `commit_sha` from step 8 — plus `artifact_paths`, the `report.json`, `summary.md`, and learnings-doc paths you wrote.

Return the verdict JSON alone.
